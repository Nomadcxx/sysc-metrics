# GPU VRAM Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Report dedicated GPU memory (VRAM) used and total per GPU, so the `sysc-shell` Control Centre
Monitor page can show it, and release it as `v0.6.0`.

**Architecture:** `GPU` gains a `VRAM Capacity` and a `VRAMValid` flag. AMD fills it from the `amdgpu`
sysfs files beside `gpu_busy_percent`. NVIDIA fills it from two extra columns on the `nvidia-smi` query
the library already runs, placed before the name column because the parser re-joins everything from
the name onward on commas. Intel reports it invalid. Nothing changes for `GPUSampler`: it calls
`readGPUs`, so it picks the field up for free.

**Tech Stack:** Go 1.26 standard library, `/sys/class/drm/card*/device`, optional `nvidia-smi`.

**Spec:** `sysc-shell/docs/plans/2026-09-25-control-centre-monitor-design.md` (D4 names VRAM as pending
sysc-metrics support). Behavioural references: Noctalia's system monitor service (amdgpu sysfs for AMD,
NVML with hwmon fallback for NVIDIA). dgop has no VRAM collector, so there is nothing to copy from it.
Tracked in `sysc-shell` bd as the cross-repository gate for this release.

## Global Constraints

- Standard library only. No CGO, no NVML binding, no new module.
- No new subprocess. NVIDIA VRAM comes from the existing `runNvidiaSMI` call; its 400ms timeout is unchanged.
- Units are bytes. `nvidia-smi --format=csv,noheader,nounits` reports memory in MiB; multiply by `1 << 20`.
- A missing or unparsable value leaves `VRAMValid == false`. It is never reported as zero.
- `Capacity.AvailableBytes` is `TotalBytes - UsedBytes`, and zero if used exceeds total.
- Intel (i915 and xe) leaves VRAM invalid. Integrated parts share system memory, and no stable sysfs total exists for discrete xe here.
- Release as `v0.6.0`: an added exported field is a minor change under the existing tags.

## Review Focus

1. `nvidia-smi` prints `[N/A]` for memory on some parts and vGPUs: VRAM must stay invalid while usage, temperature and name still fill.
2. A GPU name containing a comma must still parse whole after the column reorder.
3. AMD APUs expose `mem_info_vram_total` as a small carve-out (for example 512 MiB): report it as-is, do not guess at shared memory.
4. `mem_info_vram_used` present but `mem_info_vram_total` missing or zero: invalid, no divide-by-zero or nonsense available bytes.
5. `nvidia-smi` failing intermittently (exit status 9, seen live on this RTX 4060 in `sysc-shell`
   `sysc-495`): VRAM goes invalid in that snapshot along with usage, and an `Issue` records the failure.
   The library keeps no previous value; showing `—` rather than stale VRAM is the consumer's contract.
   Covered by `TestGPUMissingSMILeavesNvidiaInvalid`, which Task 2 extends to assert `!g.VRAMValid`.
6. Output from an older four-column query (a test fixture or a stale binary) must not shift the name into a memory field: rows with fewer than six fields fill only what they carry.

```go
// vramCapacity builds a Capacity from used and total bytes. A zero total is
// not a device with no memory; it is a driver that did not report one.
func vramCapacity(used, total uint64) (Capacity, bool) {
	if total == 0 {
		return Capacity{}, false
	}
	c := Capacity{TotalBytes: total, UsedBytes: used}
	if used < total {
		c.AvailableBytes = total - used
	}
	return c, true
}
```

`readSysfsUint(path string) (uint64, error)` already exists in `battery_linux.go:189`; reuse it. Do not
read byte counts through `readSysfsInt`, which accepts negative values.
